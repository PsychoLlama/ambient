# Compile Time

A comptime call runs an ordinary function during compilation and splices what it gives into the program. Code is generated by a function over trees, and a value is the tree of its literal, so a function over values is the plain case. It is the single mechanism behind build scripts, code generation, and derived types.

## Calls

- A comptime call is marked at the call site; the callee is any function.
- There is no separate class of compile-time functions.
- An argument is an expression of [singleton type](types.md), a closed type, a closed row, or the name of a definition.
- A parameter's type says what it receives: one of an ordinary type receives the argument's value, and one whose type is a tree receives the tree.
- An expression is never handed over as code not yet evaluated: it is passed as the value its type says it has, so no name in it comes to mean something else where it lands.
- The result replaces the call before checking; the enclosing definition's hash covers the result, not the call.
- A comptime call runs only when its enclosing definition is demanded by a [build](build.md).
- Checking the enclosing definition depends on the callee's [hash](definitions.md), not only its interface, because the result is the enclosing definition's content.
- A definition whose content depends on a comptime call that depends on that definition is an error.
- A [fault](values.md) in a comptime call is a compile error at the call.
- A comptime call is compiled and run for the machine doing the build, whatever the program is being built for.
- A comptime call is never told what a program is being built for, so a definition has one hash under every [target](targets.md). What differs by target is a [tool](tools.md)'s to make.

## Splice positions

- In expression position the result is spliced as an expression: an [unanchored](values.md) value as a literal of singleton type, a tree as the code it is.
- An expression tree a call gives names nothing local to where it is spliced; code that needs what is there is a function, which the site calls.
- In type position the result is a type tree.
- A type definition whose whole content is a comptime call is a derived type: it is the type the tree stands for, and has the [hash](definitions.md) of that type written out.
- A function definition whose whole content is a comptime call is a generated function: it is the function the tree stands for, and has the hash of that function written out.
- A generated function's tree says what it takes and gives and its row, so what names it is checked against that without its body.
- In module position the result is a set of definitions, forming the whole content of a generated module.
- A generated module is a module like any other in its [package](packages.md): it has a path, and imports of its own, which are all its call can name.
- The call gives definitions by name, each a function, a type, an ability, or a tag, and public or not; the module has those and no others.
- What a generated module defines is not in scope for its own call, so a call cannot depend on what it gives.
- Importing a generated module runs no call: what it has is asked for by each definition that uses a name from it. So a module the call reaches may import it, and only a definition the call reaches cannot name what it gives.
- An import of a name a generated module lacks is therefore an error of the definitions that use it, and of checking the package, not of reading the import.
- A module cannot re-export what a generated module has while its call needs that module's members.
- A generated module is the only place a comptime call creates [symbols](symbols.md); they are ordinary symbols.
- A comptime call never adds a name to the scope it is written in; a generated module's definitions are reached by importing them, like any other module's.

## Trees as values

- Comptime functions receive and return types and definitions as [trees](trees.md), built with the same builders as everything else.
- A definition named as an argument is received as its tree and its checked interface, so a function that generates code sees types and never text.
- Reading a definition is an observation in the call's [trace](memoization.md): the call runs again when what it read changes.
- Derived types such as a subset of a record's fields or a function's return type are ordinary functions over type trees.
- A type's tree is that of its normal form: a name for a type is gone from it, so two ways of writing one type give one tree.
- A tree refers to a definition by a reference: a value that says which definition outright, so nothing in a tree is looked up by name where it lands.
- A function is handed a reference for a parameter whose type is one, when its call names a definition. The name is resolved where it is written, as any name is.
- A function comes by a reference to what its own module names the same way: by a comptime call of the function that gives back the reference it is handed.
- A type that refers to itself has the tree of its definition, with a reference where it names itself.
- A definition of a generated module refers to another of the same module by its name there. The function that gives a module does not know where its call is written, and a tree that said would be a module's in one place only.
- A reference is plain data, read and matched like the rest of a tree. A mark only the compiler makes would be lost in a tree: a test cannot tell a marked value from one shaped like it, so a tree holding one could not be matched.
- A comptime call operates on closed types only; a type parameter is never an argument.
- Type-level computation therefore never runs inside generic checking.
- A spliced tree is checked exactly as a written one; comptime cannot bypass the checker.
- A function's result is spliced as code when the type it is declared to give is an expression's tree, and as a value otherwise.
- A reference in spliced code must be one that code written at the call could make: to a definition of the call's own [package](packages.md), or a public one in a module its package lets others reach.
- A function can make a reference up, so this is what keeps spliced code from reaching an [extern](externs.md) past the ability that guards it. It also means generated code cannot use what is private to the package that generates it.
- A derived type's tree may refer to any type. The normal form of a public type names the recursive types its package keeps private, and naming a type gives no way to make a value of it.
- TODO: a reference names its package as the workspace does, so a tree that is stored or sent means something only there.
- A function named as an argument for a parameter that takes a type's tree is handed the type it has.
- An [ability](abilities.md) in a function type's tree comes with the types it takes and gives, so a function that is handed a row can make a [handler](handlers.md) for each ability in it.
- The standard library puts trees of code together from functions, so that no code counts a local by hand: a piece of code is a function of how many locals are bound around it, and what binds one hands its body the code that names it.
- A function in a tree binds its parameters by position: a tree names a parameter by its number among those of the functions it is inside, so no tree binds a name.
- What spliced code names is read when the call is checked, and is no part of what was known before: a definition whose content came from such code is checked again when any definition that code names changes.
- A tree value carries no [metadata](trees.md); a comptime function reads names and doc comments by performing a verifiable build ability, so the read is in its [trace](memoization.md).

## Authority

- A comptime function's effects are abilities, so its row states everything it can touch.
- The compiler runs comptime calls under a build [target](targets.md) whose abilities read from the developer's machine.
- The build target binds the [build abilities](tools.md#build-abilities). A path is from the directory of the package the call is written in, and names only [files of that package](packages.md#layout).
- A [package](packages.md) declares the build abilities it needs; granting them is its workspace's [approval](releases.md#approvals).
- A comptime call runs under the grants of the package that contains the call site.
- An ungranted ability is a compile error at the call, naming the ability.
- A comptime call with an empty row needs no grant.

## Caching

- Comptime calls are [memoized runs](memoization.md); a call reruns only when something it observed changed.
- Each call is a run of its own: none sees what another did, and no result depends on the order calls are run in.
- A result gathered from many calls is never accumulated by them. Each gives [annotations](annotations.md) in its tree, and a tool collects those a program reaches.

## Unsettled

- An expression's tree has a match, whose patterns bind by position as a function's parameters do: a binding is the local after those around the match and those its pattern bound before it.
- An operation in a tree is named by its word, which is also how source text can write any operation: `@add(left, right)`.
- TODO: an expression's tree has no cell or task, so code that does one calls a function that does. An expression is not yet handed to a function as a tree.
- TODO: an ability with type parameters has no tree, so neither has the type of a function that takes one.
- An argument of a comptime call may name an ability, for a function that takes a reference to one.
- A function's tree and an ability's say their type parameters, each by its bound or by nothing; a type definition's says how many it has. A type's tree names one by its position, as an expression's names a local.
- A type parameter is named only inside the definition that has it: a derived type's tree names none.
- TODO: a generated module defines no key, target, or native handler, and its externs perform nothing.
- A derived type refers to itself as any tree refers to a definition: by a reference its call makes. Its call cannot name it, since naming it asks for the type the call has yet to give; nor can a generated function's call name that function, though its body may call it.
- A type that refers to itself with arguments has a tree: the reference, and the tree of each argument.
- A generated node has no [span](trees.md). An error in code a call gave is reported at the call, with that code written out around the node the error is at, which is marked.
- A frame of a [trace](errors.md) in generated code is at the call that gave it.
- Code written out for a report names each local by the order it was bound in, since a tree binds no name.
- TODO: code is written out for a report in a format of its own, which is not the canonical one a [tree is written back](trees.md) in.
