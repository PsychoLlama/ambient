## Structure

- `spec/`: source of truth for the language design. The implementation follows it; change the spec first.
- `crates/ambient`: the implementation, a library plus an empty binary. Module docs name the spec page each module implements.
- `crates/ambient-host`: what loads and runs a compiled program, with no compiler in it: trees, values, parts, the native loader, the native side of `system`, and launching. `ambient` gives its modules again at the paths they had (`ambient::core`, `backend::native`, `host`), which is how the bullets below name them.
- `crates/ambient-launcher`: the binary a built program is put after. It links `ambient-host` and nothing of the compiler; keep it so.
- `crates/ambient-js`: the JavaScript host of a module built with `ambient build --module` (`js/host.js`): ES modules with no dependencies, which know of no browser and no Node. `constants.js` is written from the runtime by the crate's `build.rs` and never committed; restate no constant in JavaScript. It restates what `backend/wasm`'s host does; where they differ, that one is right.
- `crates/ambient-runtime`: what compiled code calls. Built natively into the compiler, and for wasm32 by `crates/ambient/build.rs` as one relocatable object.

## Invariants

- Text is read by `ambient::syntax` into the same surface trees the builders make, through the builders. Tests still build programs with `ambient::builder`; only tests of the syntax itself, and of whole programs on disk, use text.
- Every stage result is stored under a key derived from the content of its inputs (`engine/mod.rs`). A stage's compute function reads nothing that is not in its key.
- The compiler itself is an input no key names: `build.rs` hashes its source into `AMBIENT_BUILD`, and `Engine::stage_if` stores under the key and that. The host has a build of its own (`parts::BUILD`: its source and the runtime's), which is all compiled parts are held to.
- A comptime call takes only abilities its package is granted (`Sources::grants`), checked at the call before it runs; the check key of a definition with comptime calls covers the grants.
- A package on disk grants its comptime calls abilities in its manifest (`grants`); they run under `system.build`, whose native side (`cli/building.rs`) is made for the package a call is written in and reads only files under that package's directory, through `project::Files`. `cli::engine` is the one way a command makes an engine.
- A comptime parameter of type `tree.Type` (`library/tree.ab`) is handed the tree of the type its argument names (`checker/reflect.rs`): the normal form as a value. The check key covers the type, as it does any the body names. One of type `tree.Reference` is handed which definition its argument names; a tree refers to definitions only so, never by a name to resolve.
- A derived type (`DefinitionKind::Derived`, `engine/generate.rs`) is a comptime call checked as the body of a function the engine writes; `checker/reify.rs` reads the type from the literal it was spliced as. From there on it is a type definition whose content is that type.
- A generated function (`DefinitionKind::Generated`, `engine/generate.rs`) is a comptime call that gives a `tree.Function`, read as a resolved function (`checker::defined`) whose names must be nameable from its package. Its signature, interface, and check are that function's, and no node of it has a place in the text.
- An error in code a comptime call gave is at the call, with the code written out and the node marked (`surface/shown/`, `Engine::shown`): the checker keeps spliced code as text (`Noted::given`), and the engine the node of a generated function. `cli::report` is the one way a command reports an error.
- A generated module is written as one definition, `surface::GENERATOR` of kind `DefinitionKind::Module`, beside its imports. `Engine::made` runs the call for resolved definitions; `members` offers them and `resolve` gives one for a symbol the module's table lacks, so its own scope never holds them.
- What reads a tree is told the module it is the content of (`reify::Home`), which is where a reference to a definition `beside` it leads; no other tree has one. A type parameter in a tree is a position, held to how many its definition has (`reify::parameter_within`).
- A scope holds an import from a generated module unopened (`Scope::generated`), so building a scope runs no call. Resolving a definition asks for the members of those it names through (`Engine::given_to`), and its key covers them; that is where a call that depends on what it gives is a cycle.
- A comptime call of a function declared to give `tree.Expr` is spliced as code (`checker/code.rs`): the tree becomes a surface expression, each definition it names must be nameable from the call's package (`Evaluate::nameable`), and it is checked as if written there. Its locals are numbered past any resolution gave.
- `library/code.ab` builds `tree.Expr` for a generator: a `Code` is a function from how many locals are bound around it to the tree, so `code.function` and `code.bind` hand their bodies the locals they bind. Add a builder there for each node `tree.Expr` gains.
- What spliced code names is not in the check key: the checker asks for it (`Error::Reaches`), `Engine::check_function` checks again with it, and the result is kept with what was read of each (`Checked::reached`) and reused through `stage_if`.
- Checking is re-entrant: a comptime call compiles and runs its callee mid-check (`engine/run.rs`). The check key covers the callee's hash, which is what keeps the result a function of the key.
- A result that observed the world is stored with what it observed and reused through `Engine::stage_if`, which looks again. Only native code is outside a key, so a trace is the native calls a run made.
- Names, docs, and declaration order never reach a hash, but for one case: an ability, a key, an extern, and a tag are told apart by module path and name (`Symbol::identity`), which their trees hold and their stage keys cover. In a core tree names otherwise decide one thing: the stored order of a union's members, and so slot numbering.
- An operation is a `core::Primitive` and a runtime entry of the same name; `types::Env::operation` types it for both checkers, and the checker picks which one an operator means (`checker/operators.rs`). Adding one touches those and `lir/steps.rs`, and no backend.
- A backend only translates `lir`; anything about semantics belongs in `lower.rs` or the runtime, so both backends get it.
- The native backend answers the common case of a few operations inline (`backend/native/emit/fast.rs`): immediate integers, words that are the same, a count of what is no object. Each gives exactly what its runtime entry would and calls the entry otherwise, so the entry stays the definition.
- Layouts and the calling convention are defined once, in `ambient-runtime`; never restate an offset in a backend.
- Every function's first parameter is its bindings: a record keyed by ability, or null. The checker tracks what is bound (`checker/abilities.rs`); lowering only threads the record (`lower/abilities.rs`).
- A record holds a method as a closure of its own kind over a function the checker writes (`checker/methods.rs`), with a null capture for the record; `amb_record_get` fills it in on a copy, so a record never holds itself. Anything that copies a field out of a record goes through `record::read`.
- A method call (`surface::Expr::Send`) means a field of a record, or for a built-in shape the public function of that name in its module of the standard library (`checker/sends.rs`); nothing else adds a method. Resolution cannot know the type, so the engine gathers the function for every shape into `Env::methods` and the check key (`engine/environment.rs`).
- A list is a view of a buffer that later lists share (`ambient-runtime/src/list.rs`); a push onto the list that ends its buffer writes into the room after it. Read a list's members through `list::members`, never `words`.
- Bytes are a shape of their own (`ambient-runtime/src/bytes.rs`), laid out as a string is and never tested as one; a host reads either through `amb_string_bytes`. One written out (`0x[89 50]`) is a `Literal::Bytes`: a constant the runtime makes from the block's text, as it does a string.
- An iterator is a shape of its own (`ambient-runtime/src/iterator.rs`): a function that steps, or a list or a range the runtime steps. `core::Expr::Step` asks for the function and calls it, or has the runtime advance (`Lowering::step`); everything else about iterators is library code over a step (`library/iterator.rs`).
- A tag (`DefinitionKind::Tag`) resolves to a type definition: the literal type of the tag its identity names. A name in value position falls back to the type namespace, and the checker gives the value only for such a definition (`Checker::tag`).
- A brand (`DefinitionKind::Brand`) resolves to a type definition, `Type::Brand` of its identity, as a tag does; `T & Brand` is `Type::Branded`, whose normal form is an unbranded type under brands in order (`types::branded`). A call of a brand's name in its own module brands (`Checker::branding`, `core::Expr::Brand`).
- A brand on a type is erased wherever a program runs: lowering passes the value through, and descriptors and function type names are those of the type under it. So a branded type is never tested for (`Env::tests`), only what is under it, and only where narrowing by that is enough.
- A handle is a shape of its own (`ambient-runtime/src/handle.rs`, `Value::Handle`): a brand's tag and a number that is its host's. A bare brand type is its type, tested by the tag (`descriptor::HANDLE`).
- The runtime queues each handle it reclaims, and a host drains the queue through `Waits::dropped` (`Program::heard`, `Guest::heard`): before native code runs, in the wait loop, and after a call. Both backends drain at the same moments, so a scripted world is left the same.
- A key is a definition in a namespace of its own (`Namespace::Key`); a record names one where it names an ability (`Key::Ability`), and `Env::holds` is the one rule for what may be held under it, which both checkers ask.
- A merge names the keys whose methods receive the merged record (`core::Expr::Merge::methods`): exactly those its type lists as methods. The runtime binds every other method to the record it came from, so no method meets a receiver nothing checked.
- A module named in a row is expanded to its public abilities by the resolver (`Resolver::row`), from the scope, which the resolve key covers.
- A row is ordered by identity wherever it reaches a core tree, never by the order it was written in.
- A program is `Engine::program(entry, target)`: a root function the engine writes (`engine/program.rs`) and then checks, hashes, and compiles like any other.
- Compiled code reaches native code only through `amb_native` and an index the loader fills in; a host supplies `Natives` by package and the extern's module path and name.
- Native code reaches its program only through `native::Running`, which each backend's dispatch implements. What it loads is held until its result is encoded, so nothing of the program is borrowed while it runs.
- Native code calls back through `Running::call`, only a function read for the call it is in (`value::Live`): a decoded function is a copy that lost its cells and handlers. The runtime entry is `amb_call_among`, or `amb_call_back` in a program linked without suspension.
- An extern is handed the handlers of its declared row and nothing else bound: a tuple in the row's order (`lower/native.rs`). `Running::perform` finds one by the ability's package and path (`parts::Native::row`, `native::bound`).
- A task that suspends beneath native code is resumed where the native code stands (`ambient-runtime/src/task/back.rs`): it is `pinned`, other tasks take turns there, and one that only the world could wake unwinds as `Fault::Pinned`. No lowering knows of it: an extern that does not answer later is never a point.
- A wait is written once in the runtime, as a step that says the task is suspending and is asked again on its turn (`task::waiting`). Whatever suspends goes through it; the scheduler never knows how a task is kept.
- The tasks waiting on a cell are a ring the cell names the first of (`ambient-runtime/src/task/watch.rs`), so a change costs only what waits on that cell. A task leaves the ring before it is cancelled and as each step of its wait begins, so a cell is never named by a task that is over.
- A task's number is its place in the scheduler, which the next task takes once it is over (`task/places.rs`); a join's is the same. Whatever names a task by number stops naming it in `Scheduler::finish`: the join that started it.
- Natively a task is a stack (`ambient-runtime/src/task/stack/`, `ambient-host/src/native/stacks.rs`): the host puts `Stacks` in the context, a wait parks inside its step, and a turn resumes the stack.
- `Backend::stacks` says a backend's tasks are stacks, and the engine then compiles every function `still`. The native emitter refuses a function with points.
- In WebAssembly a task suspends by unwinding with the context's mode set, and resumes by its functions being called again (`lower/resume.rs`). The runtime is built there without any stack state (`task/stack/none.rs`), which `tests/footprint.rs` holds it to.
- A wasm function that may suspend keeps where it is in one local (`backend/wasm/resume.rs`): points are numbered in the order they are reached, so a `Let` asks with one comparison whether its value is still to compute. It keeps its locals in one block every point shares, and takes them back in one at its start.
- A host that sees the entry unwind while suspending calls `amb_schedule` and the entry again, on either backend: natively `amb_start` runs the root on a stack and that second call resumes it.
- A native handler declared `suspending` is called through `amb_native_wait` (`ambient-runtime/src/task/wait.rs`): native code takes a ticket (`Running::later`), the task suspends, and the host's loop takes answers from `Waits` when the scheduler leaves the mode `WAITING`. A task that leaves a wait tells the host at once, through the native entry with the index `FORSAKEN`.
- A program is linked closed (`Engine::link`) or open to loading (`Engine::link_open`, `Parts::open`); only an open one is loaded into. A closed program in which no core tree `suspends` is compiled `still` (`lower::Form`, `engine::compile::Mode`): no operation is a point.
- A function with no point (`lir::Function::points`) is left as lowered and emitted without what resuming takes; a backend must not read its resume target.
- A tail call unwinds with the call pending in the context, arguments and all (`lower/tail.rs`, `Op::Tail`), and every other call is followed by `Op::Bounce`, which makes it (`ambient-runtime/src/task/tail.rs`). Whatever calls compiled code from outside goes through `amb_start`, never a code address.
- A tail call a function makes of itself (`Form::own`) is `Op::Again` inside an `Expr::Loop`: the loop owns the parameters it is given from the second turn on, in locals after the rest. A parameter handed on unchanged is not touched.
- A function that makes a call that takes stack asks how deep it is as it starts (`Op::Enter`) and says so before each such call (`Op::Depth`, `Op::Bounce`; `ambient-runtime/src/task/depth.rs`); past `DEPTH` words it faults. A host runs a program inside `backend::stack::roomy`, which has the stack for that depth.
- An all or a first over a list (`Primitive::ListAll`, `ListFirst`; `library/tasks.ab`) lowers to the `Op` the written form does: `amb_all` takes a tuple or a list and gives the same.
- A task's body is a closure that takes nothing; the checker makes one for each branch, spawn, and cleanup (`checker/tasks.rs`), so they capture locals and bindings as any closure does.
- A using (`surface::Expr::Using`) binds as a let does; the checker reads what the value holds under `ambient.cleanup.dispose` (`library::dispose`, which the check key covers) and registers a call of it (`checker/tasks.rs`). Resolution never changes the shape of a tree.
- Whatever must happen on every way out of a block (cleanups, closing a group) is lowered as a `Try` whose recovery holds the unwinding, does the work, and rethrows (`lower/tasks.rs`).
- A trace is gathered only while a fault unwinds, or an abort to a token made `traced`: lowering wraps each operation either can leave in a `Try` that notes its position (`core::Expr::positions`), so code that does neither pays nothing.
- An abort handler that takes one parameter more than its ability is handed the trace (`core::Handler::traced`, `Env::abort_handler`, `Op::Traced`); a native handler of an ability that does not return always is. Nothing else reads a trace: `library/errors.ab` puts it in an error where one is caught, and `launch` where one reaches the root.
- A native function's locals are in a Cranelift stack slot. In wasm they are the function's own locals, or past `emit::VALUES` of them a frame on the runtime's stack (`__stack_pointer`, which the runtime exports): a local is live to the end of its `Let`, and many as values make an engine's compile time quadratic.
- A tree nests at most `core::DEPTH` levels (`core/depth.rs`): the builder's validation, `Engine::check`, and decoding each refuse a deeper one. Walks recurse, so every `Engine` entry that touches a tree runs inside `lower::deep`.
- Lowered code nests once per bound value, so whatever makes, walks, or drops a `lir::Function` runs inside `lower::deep`, on a stack with room for it.
- Compiled code is position-independent: it reaches definitions through slots and the runtime through entry points, never by address.
- A name reaches a definition through a module's members (`engine/scope.rs`): its own definitions and its re-exports, which keep the symbol of what they alias. Another package is reached only through its library module and the modules that lists.
- The standard library is a package installed into a workspace on request (`library/`). Its modules are `.ab` source, embedded and read at install; only its library module is built, since fault kinds are tags named by the runtime, never restated.
- A collection that is not a runtime shape is a record of methods over a private tree, written in the library (`library/map.ab`); `get` of a missing key is null, as for a list.
- JSON is library code over strings and the map (`library/json.ab`): a recursive union, read by functions that take a position and give a value and the position after it.
- A method of a built-in shape is a public function in `library/<shape>.ab` whose first parameter is `self`. Generic library code narrows with a match and a binder, never a cast to a type parameter, which would make it need type arguments as it runs.
- The reader (`syntax/`) resolves nothing: it tracks only the locals of the function being read, to tell `record.field` from `module.definition`. Statements, early returns, `if`, and the operators the language lacks are arranged into existing nodes (`syntax/parse/block.rs`, `expr.rs`). That stands in for the written tree of `spec/trees.md`: keep each arrangement a function of its own, so it can be lifted into a pass over one.
- The reader marks each expression with where it was read (`surface::Expr::At`) and takes the marks out when a definition is done (`syntax/place.rs`), into a position per node in `Expr::children` order. No other code meets a mark; `children` and `children_mut` are one macro so the order cannot drift.
- The checker marks each core expression with the node of the body it was made from (`core::Expr::At`, `Checker::marked`) and takes the marks out when a definition is done (`core::Expr::origins`), into a node per position (`checker::Noted`). No other code meets a mark; `Engine::origin` and `Project::place` turn a frame of a trace into a line (`cli/trace.rs`).
- A checking error is at a node of the resolved body, which has the shape of the surface one: the checker notes the innermost expression that failed (`checker/blame.rs`), `Engine::blame` gives its number, and `Project::report` its line. `Checker::check` holds the last part of a let, a match, and a using to what is expected, so the error is at the leaf.
- A function in a block that names itself is read as the one method of a record and taken from it (`Parser::function_in_block`, `Parser::own_receiver`), so its body reaches it through the receiver. No node says a closure holds itself.
- A pattern's type that cannot be tested for is replaced by the nearest that can (`Env::nearest_test`, `Checker::asked`) before anything narrows by it, so the core tree and the core checker only ever see a test that can be made. A cast to one is a match the checker writes (`Checker::cast_near`).
- A match of one arm that binds its subject as a type is an ascription (`Checker::ascribed`): the subject is checked against the type and nothing is tested. The core tree says so (`core::Expr::Widen`), since the core checker would otherwise infer less than the binder was said to hold. It is what the reader makes of `let name: Type = value;`.
- Names the reader makes up start with `__`, which no program may write.
- What needs a world is the `system` package (`system/`, `spec/targets.md`), installed beside the library; `ambient` holds nothing that does. The command-line target is `system.cli` (`system/lib.ab`); its native side is `host/`, where every handler goes through `host::World`, and one that takes time begins `host::Work` and is answered later. The real process waits on threads that send what they got (`host/pending.rs`, `host/network.rs`); only the program's thread touches a value. Tests run programs over `support::scripted::Scripted`, never the real process.
- `system.code` is native code over an engine with an empty workspace (`host/code.rs`): a pack leaves nothing out, so compiling one needs nothing else. It compiles for the backend `Running::backend` names (`backend::named`), and what `code.load` takes is `Parts::encode`. Loading is the host crate's; packing and compiling need the compiler, and are added to its handlers (`host::compiling`).
- A `system.cli` program is compiled by `host::link`, never `Engine::link`: open if its row reaches `code.load`, and with a pack of its entry (`Linked::trees`) if it reaches `code.pack`. A root binding the row does not reach is not linked, so the externs of the parts say which.
- `throw` is an ability of the library like any other (`library/errors.ab`), re-exported beside `Error`; each standard target binds it to an extern `thrown` of its own package, both of which `launch::started` supplies and reports as it does a fault.
- A lambda with no row takes the row of the function type expected of it (`Checker::infer_as`, `asked`); with none expected it captures everything.
- `ambient test` runs each `test_*` function that takes nothing as its own program under `ambient.test.tests`, whose one extern is the check (`cli/test.rs`); `cli::Launch` is the one way a command runs a program.
- An executable is a launcher with a program after it (`launch::Built`): encoded parts, the names and places a report takes (`launch::Frames`), a length, and a mark. A launcher looks for the mark in its own file as it starts (`launch::own`); `launch::started` is the one way a compiled program is run and reported, built or not.
- The launcher is `crates/ambient-launcher`, a host with no compiler, which `crates/ambient/build.rs` builds and the command holds (`cli::LAUNCHER`). A program that packs or compiles code (`host::compiles`) is put after the command's own file instead.
- A package on disk is read through `project::Files` (`project/`), and `cli::Session` is handed its files, store, and world, so `tests/cli.rs` drives the command line in memory.
- The core checker (`verify/`) accepts what `checker/` makes and nothing looser; `support::run` verifies every definition it runs. Typing rules live in `types::Env`, which both checkers ask.
- A received definition (`engine/pack.rs`) is an `Open` under a made-up symbol: it is verified, then hashed, compiled, and linked like any other. It has no surface tree and never reaches the store.
- A definition holds its own hash (`DEFINITION_HASH`), so a host reads a function value as a hash and captures (`value.rs`), and makes one of a definition the program has (`native::Inside`); what it captures is trusted.
- A native `Program` is units: each `Program::add` lays out a block (`statics::plan` with a `Base`) that refers to what the program already has by address. `Engine::link_to_load` makes the parts.
- A wasm program is one module: its compiled functions and the pieces of the runtime they and its host reach (`backend/wasm/link/`, `spec/linking.md`). A compiled body leaves room where it calls the runtime and says where (`backend/wasm/code.rs`), since no function has an index until the module is put together.
- What a piece of the runtime refers to is read from the object's relocations (`link/object.rs`), never listed by hand. `tests/footprint.rs` holds a program that does nothing to a size.
- The runtime is `no_std`, and in wasm has its own allocator (`heap.rs`), unlocked state (`state.rs`), and a panic handler that traps. Use `core` and `alloc` there, never `std`, and no `format!` on a path every program reaches.
- Linking cuts the standard library's panic functions to a trap by name (`PANICS`, `link/object.rs`), since they format before the handler runs.
- Wasm loads a `wasm::unit` module over a `wasm::open_module` program (`backend/wasm/units.rs`, wasmtime), with what loading keeps in the store's `State` so a host call can load too. The unit imports each definition's address by hash (`known`), zero meaning it lays out its own; modules describe themselves through exported globals (`root:`, `definition:`, `native:`).
- A unit is linked for the pieces its target has (`wasm::unit(parts, has)`, `link::For::Unit`): it imports those by hash (`piece`), carries the rest, and exports what it carries (`piece:<hash>`, `state:<hash>`). Its pieces' data is in a block its `init` takes, reached through globals (`link/unit.rs`), and is never given back.
- A state is imported as an address by hash (`state`), zero meaning the unit uses its own copy. Only writable data is state; constants are always carried.
- `statics::plan` names a part's root or definition (`Field::Root`, `Field::Definition`) and an extern (`Field::Native`) without saying where; each loader resolves them.
- A loaded block is a unit (`ambient-runtime/src/unit.rs`): it starts with a count, and a word naming the unit precedes each definition, fixed object, and constant descriptor in it. Closures, cells, type arguments, and dependent units hold the count; `Program::reclaim` drops units at zero.
- `Op::Copy` of a local, capture, or constant takes a reference (`lir::Value::counted`); a loaded unit's strings are counted, not pinned.
- A function type with type parameters is `Type::Generic` around a function type, its parameters `Type::Bound` indices; `Reference::Parameter` is only ever a parameter of the definition being checked. A value of one is instantiated before it is called (`core::Expr::Instantiate`, `amb_instantiate`), which copies the closure only if its definition says it is handed type arguments (`DEFINITION_TYPES`).
- A generic function that needs its type arguments reads them from its closure, after its captures and bindings (`lower/types.rs`, `ambient-runtime/src/scope.rs`), so it is never called through its slot. Which functions need them is `Engine::handed`, the least answer over what hands them on to what; lowering is told through `lower::Form`, and the compile key covers it.
- How a recursive type varies with its parameters, and whether unfolding it ends, is worked out when an environment is gathered (`Env::settle`, `types/variance.rs`). Two uses of one definition are compared by arguments first, and one that is not `finite` is never unfolded against itself.
- Subtyping is decided only when checking (`types/relate.rs`). The runtime compares two types for sameness alone, for casts to cell types (`ambient-runtime/src/same.rs`); a cast to a function type compares one word, the name of the type (`backend/identity.rs`), which a definition carries.
- A function whose type depends on type arguments carries a descriptor of it instead of a name (`DEFINITION_DESCRIBED`, `link::says`), and only if it is handed them. A cast reads it in the arguments the closure holds (`closure::described`).
- A native `Program` keeps a list of its live cells and empties them when it drops (`ambient-runtime/src/cell.rs`), since counting never reclaims a cell that reaches itself. In wasm the instance's memory goes as a whole.
- `Parts::encode` is compiled code for a host with no compiler (`ambient-host/src/parts/encode.rs`), refused by another backend, format, or build of the host. Bump its `FORMAT` when `Parts`, a layout, the calling convention, or a runtime entry changes.
- A value has one encoding (`exchange.rs`); `decode` accepts only what `encode` produces. A host sees inside an iterator (`value::Source`), and only one that keeps what its source keeps (`Source::keeps`) is decoded or made in a program: the runtime steps without looking.
- `core::Tree::resolved` defines every hash: the tree's encoding with slots replaced by hashes and unions ordered by that. `Tree::encode` is the stored form, which names can order; never hash it. Changing either or the node set means bumping `FORMAT`.

## Testing

- Tests build a `Workspace` in memory and run an `Engine` over a `MemoryStore`; nothing touches disk, except `tests/disk.rs`, which tests the `DiskStore` under the system's temporary directory.
- Programs are built with builders. Text is for tests of the reader, of library methods (`support::text`), and of whole packages.
- A program is run with `support::run` or `support::run_with`, which run it natively and in wasmtime and fail if they disagree or if either leaks an object.
- `ambient-js/tests/host.rs` builds a program as a module and runs `js/*.test.js` under Node's own runner. JavaScript is tested nowhere else, and only what the host itself does.
- An incremental test builds twice over one store and asserts on `Engine::ran` and `Engine::reused`.
